Technical detail
gpt-oss-120b at 1M tokens, fp8 KV cache: serves users from 4× B200 SXM (1 model on 4). With 4× B200 SXM (1 model on 4):
10 users guaranteed, 20 likely, at 44 tok/s (30 to 59, ±33%, not precise enough to decide) each; reading 1M tokens: 33.5
s (20.9 to 46.0 s, ±37%).
Scenario "documents": each request brings 512k new tokens to read and generates 500; at least 20 tok/s per user. For a
chat (the conversation stays in the cache) use --prompt-cache 80.
Note: 1M tokens is beyond the model's own maximum (128k): the engine refuses it without a RoPE override (YaRN, e.g. vLLM
--hf-overrides), and the quality beyond the context the lab declares is not guaranteed.

(3) partly supported: On SM12x the gpt-oss selector keeps only BF16-activation backends: TRTLLM (SM10x), OAI Triton (CC
    < 11.0, SM120 explicitly excluded) and FlashInfer CUTLASS BF16 (SM90 only) all fail, so MarlinExperts (weight-only
    MXFP4) serves the experts. Workaround: --moe-backend b12x after pip install vllm[b12x] selects the native SM12x B12X
    MXFP4 MoE kernels (code path verified; not verified at runtime). FA2 does not support fp8 KV, so vLLM selects
    another attention backend (FLASHINFER for most models, with Q in bf16). There are open bugs on this path: with pip
    and no nvcc, FlashInfer is selected but does not compile (crash 'Could not find nvcc'), and with checkpoints that
    have q_scale the output is wrong. Workaround: --attention-backend TRITON_ATTN. In v0.31.0 the OAI Triton MoE
    excludes SM120 and the FlashInfer CUTLASS MXFP4 BF16 path is SM90-only, so the gpt-oss experts run on Marlin
    (weight-only MXFP4, BF16 compute). Attention runs on a sink-capable backend (Triton). (source:
