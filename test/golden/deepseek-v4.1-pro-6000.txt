Technical detail
DeepSeek-V4.1-Flash at 32k tokens, fp8 KV cache: fits in memory from 8× RTX PRO 6000 Server (1 model on 8), but the
engine does not start (Dense MLA: TRITON_MLA accepts fp8 KV from SM89, but on RTX PRO 6000 the decode kernel
_fwd_grouped_kernel_stage1 requires 102400 B of shared memory against a limit of 101376 and crashes (num_stages=1 only
with BLOCK_DMODEL>=1024; fix not merged). Workaround: Use --kv-cache-dtype auto/bfloat16. On sm120, vLLM runs
DeepSeek-V4.1 through its FlashInfer SM120 backend, which declares 128-token KV blocks (the indexer also uses 128
outside Hopper), while the sliding-window cache uses 32-token pages. The SM120 sparse MLA kernels of FlashInfer
0.7.0.post1, the version pinned by vLLM 0.31, are instantiated for 64-token pages only, for both decode and prefill. No
block size works for every layer, so the server stops during warmup. This applies to every sm120 GPU (RTX 5080/5090, RTX
PRO 6000), on Linux as well. (source:
https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/attention/backends/mla/triton_mla.py#L97-L103)); no layout of
the catalog runs it.
Scenario "documents": each request brings 16k new tokens to read and generates 500; at least 20 tok/s per user. For a
chat (the conversation stays in the cache) use --prompt-cache 80.

    the decode kernel _fwd_grouped_kernel_stage1 requires 102400 B of shared memory against a limit of 101376 and
    crashes (num_stages=1 only with BLOCK_DMODEL>=1024; fix not merged). Workaround: Use --kv-cache-dtype auto/bfloat16.
    On sm120, vLLM runs DeepSeek-V4.1 through its FlashInfer SM120 backend, which declares 128-token KV blocks (the
    indexer also uses 128 outside Hopper), while the sliding-window cache uses 32-token pages. The SM120 sparse MLA
    kernels of FlashInfer 0.7.0.post1, the version pinned by vLLM 0.31, are instantiated for 64-token pages only, for
    both decode and prefill. No block size works for every layer, so the server stops during warmup. This applies to
    every sm120 GPU (RTX 5080/5090, RTX PRO 6000), on Linux as well. (source:
    https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/attention/backends/mla/triton_mla.py#L97-L103)
(2) Dense MLA: TRITON_MLA accepts fp8 KV from SM89, but on RTX PRO 6000 the decode kernel _fwd_grouped_kernel_stage1
    requires 102400 B of shared memory against a limit of 101376 and crashes (num_stages=1 only with BLOCK_DMODEL>=1024;
    fix not merged).
(3) Pipeline parallelism does not work (wrong output, counted as not starting): The CUDA DeepseekV41ForCausalLM declares
    SupportsPP and starts, but Model Runner V2 passes input_ids=None to non-first PP stages and the engram n-gram hashes
    are computed only when input_ids is present, so an engram layer (layers 1 and 14 of 40) placed on a later stage
    silently skips its engram injection. With the default even split pp=2 keeps both engram layers on stage 0, while
    pp>=3 moves layer 14 to stage 1 (code reading, not run).
